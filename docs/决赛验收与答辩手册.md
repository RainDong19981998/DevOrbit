# DevOrbit 决赛验收与答辩手册

> 目标：用可复核的新任务证明 Worker 自主执行、证据驱动返工、人工门禁、重启恢复和数据库真实试验。演示中始终区分本地真实执行、冻结历史证据、团队构造数据和待接入生产能力。

## 1. 决赛主张

DevOrbit 不是生成补丁的聊天机器人，而是研发交付控制面。它把 Issue、日志、代码、测试、审批、灰度和经验沉淀组织成同一个可暂停、可恢复、可审计的 Case。模型负责开放式分析与候选方案，固定策略负责权限、验收、幂等和熔断，人类负责高风险发布决定。

## 2. 主案例：陌生输入到批准交付

现场不使用默认标题。评委给出或临时输入一个新的故障描述、仓库和分支，验收条件在执行前锁定：业务结果一致、必选测试全绿、根因置信度不低于 0.80、回滚点存在、L2 发布必须人工批准。

1. 在驾驶舱修改问题标题，选择 `self-healing`，点击“运行完整案例”。
2. 展示 Leader 创建任务消息，七个 Worker 分别提交输出；每个 Worker Span 展示 Skill 版本、摘要、输入输出摘要和父 Span。
3. 第一版补丁测试失败。Leader 将真实测试日志交回 Patch Worker，第二版补丁通过 4/4 测试。强调失败结果未被隐藏，返工次数进入 Trace。
4. 系统停在 `approval_pending`。检查代码 Diff、测试制品、MCP 审计和证据链后，由现场人员点击批准。
5. 同一 Case/Trace 继续灰度、确认和知识写回。最后在“运行治理与恢复”点击该 Case，反查完整轨迹。

主案例通过条件：实际代码被应用到隔离工作区；Red→Green 测试输出可见；批准前发布工具调用数为零；批准后同一 Case/Trace 进入终态；终态归档可重新打开；Episode 带可信状态与验证条件。

## 3. 异常案例：中断恢复与证据不足

### 3.1 审批中断恢复

运行正常案例并停在 `approval_pending`，记录 Case ID 与 Trace ID，停止并重启服务。`GET /api/runs` 应显示 `restored: true`；批准后仍使用原 Case/Trace，已完成 Worker 不重复执行，证据链连续。

### 3.2 证据不足

选择 `dynamic-resampling`。首轮 RCA 为 0.58，Leader 进入 `evidence_gathering`，拉取配置变更、连接池水位和深层 Trace 后重评分为 0.91。补证仍不足时必须转 `needs_human`，不能生成补丁。

### 3.3 返工熔断

选择 `test-failure` 或设置最大补丁尝试次数。测试持续失败时，系统在上限处停止并保留失败制品，不调用发布工具。该失败假设可作为 negative Episode 供后续相关问题检索。

## 4. 数据库真实试验

执行 `npm run db-branch-smoke`。脚本在 PostgreSQL 16 中从同一 50k 行基线创建两个隔离 Schema：索引方案和查询改写方案。它先比较业务结果哈希与行数，再用七次真实 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 比较 p95，保留完整执行计划，最后验证外键和分支销毁。

报告 `reports/db-branch.json` 必须满足：

- `measured=true` 且 `executionMode=real-isolated-schema` 才能称为数据库实测；
- 两个候选的 `resultHash` 相同才允许比较性能；
- `acceptance` 四项全部为真；
- 被淘汰方案、原因、样本和执行计划完整保留；
- Docker 或数据库不可用时只报告 `skipped`，不得引用为通过数据。

本地 PostgreSQL 验证的是 PostgreSQL 兼容 SQL、隔离和执行计划。PolarDB PostgreSQL Agentic Database 分支仍需在有账号的决赛环境复跑后，才能标记为 PolarDB 实测；切换时保持相同候选、数据快照、负载、断言与报告 Schema。

## 5. 后台证据入口

| 入口 | 现场回答的问题 |
|---|---|
| `GET /api/runs` | 哪些任务活动中、从重启恢复、哪些已有终态归档 |
| `GET /api/runs/{caseId}` | 此交付由哪些 Agent、Skill、工具、测试和审批产生 |
| `GET /api/knowledge` | 成功与失败经验是否跨应用重启保存，当前可信状态是什么 |
| `GET /api/skills/registry` | 当前 Skill 版本、SKILL.md digest、绑定和回退策略 |
| 驾驶舱“执行证据” | 实际 Diff、测试制品、MCP 审计、消息与知识卡 |
| 驾驶舱“运行治理与恢复” | 部署模式、持久化方式、恢复会话和历史 Case |
| `reports/db-branch.json` | 数据库候选是否在真实引擎、相同数据与负载下比较 |

## 6. 三类职责边界

| 决策主体 | 职责 | 不允许做的事 |
|---|---|---|
| 模型/Worker | 分析证据、形成根因候选、生成最小修改、根据失败日志修订 | 自行降低门禁、签发审批、绕过测试、直接写生产 |
| 固定控制面 | 状态迁移、Schema 校验、权限、幂等、证据链、测试阈值、熔断 | 预置新 Issue 的根因、补丁或最终判断 |
| 人类 | 确认业务风险、批准或拒绝 L2/L3 动作、复盘准入 | 用口头决定替代审计回执和验证证据 |

## 7. PPT 主讲结构

主讲控制在 12 页：真实痛点 1 页；职责边界与状态机 2 页；新任务完整闭环 4 页；异常恢复 2 页；真实数据库候选试验 1 页；可复核指标与诚实边界 1 页；结论 1 页。七角色清单、测试分类、安全策略、基准细节、Schema 和完整架构移入附录。

首屏先讲“定位、验证和交付为何困难”，不先讲技术名词。价值数据只使用可追溯口径：Case 数、闭环率、人工介入点、返工次数、真实执行耗时和最终测试结果；团队仿真、公开基准、本地平台实跑与生产数据分列说明。

## 8. 决赛前冻结清单

- 使用从未运行过的新标题完成主案例，导出 Case/Trace、代码结果和测试证据。
- 完成一次服务重启后的审批恢复，核对同 Case/Trace 且无重复发布。
- 在可用数据库环境复跑 `db-branch-smoke`，只在 `measured=true` 时截图和引用。
- 若获得 PolarDB 账号，用同一试验协议复跑并保留分支 ID、数据库版本与执行计划。
- 展示一个 Skill PATCH 升级和回退；核对 Trace 中版本与 digest 随之变化。
- 统一 README、PPT、演示视频、报告中的版本、测试数、基准口径和日期。
- 运行 `npm run verify-all`、`npm run release-audit` 和交付物校验和生成。
- 断网复核主案例；准备数据库或外部平台不可用时的冻结证据，不将其描述为现场实跑。

# 无配音视频分镜与现场演示脚本（V1.0.0 · 对应 18 页路演 PPT）

演示主线按 20/50/30 结构：前 20% 架构与严密性，中间 50% 一个复杂 Case 的完整演示，后 30% Benchmark 数据与知识资产。录制版视频 126 秒（≤8 分钟门禁），必含三要素：Agent 协作过程（collaboration 场景）、Skill 调用证据（skill-trace 场景）、异常处理演示（self-healing 场景）。

## 0:00–0:20 封面与核心主张（PPT P1-P2）

"DevOrbit 不是聊天机器人——用户提交问题、仓库和分支，系统交付的是一份可以检查、批准、回放和审计的修复证据包。接下来我用一个会'骗人'的真实形态事故，演示它和普通 Agent 流水线的差别。"

## 0:20–0:40 架构与状态机回边（PPT P3-P4）

"七个职能 Worker，一条状态机。注意这两条回边：补证回边——RCA 置信度不足时系统不停止也不硬猜，而是自主生成补证计划；返工回边——测试失败时带失败日志回到 Patch Worker 二次生成。两条回边都有熔断上限。高风险动作默认停在 HMAC 签名审批前，策略门禁由确定性代码执行，不由模型绕过。"

## 1:50–2:15 主线 3：DB Branch 并行验证（PPT P8）

"涉及 Schema 变更和慢 SQL 的缺陷，从脱敏基线一键拉出两个隔离数据分支：Branch-A 索引优化、Branch-B 分页改写。同时重放事故流量——两个方案都让报错消失，但 Branch-B 并发锁等待超限、事务耗时劣化，被自动淘汰、零污染销毁；Branch-A 择优合并进 L2 审批。本地 PostgreSQL 等价语义验证，生产路径为 PolarDB Agentic Database Branch。"

## 2:15–2:35 主线 4：负面方案召回（PPT P9）

"系统不只记得什么能修，还记得什么不能碰。EP-005 记录了一次历史事故：有人把连接池从 80 调到 200 试图缓解超时，结果下游 Redis OOM 级联崩溃。本次 RCA 报告自动生成警示：调大连接池方案已自动规避。Episode 检索先按租户、服务、环境、git 版本、配置版本硬过滤——不同版本的相同报错不会误召回。"

## 2:35–2:50 主线 5：灰度回滚与知识准入（PPT P10）

"10% 灰度，SLO 违约即确定性回滚。修复后不立刻入库——15 分钟观察窗口、业务断言、复盘确认全部通过，Episode 才从 pending 转 active 进入默认召回；回滚或复发则转为负面证据立即可召回。"

## 2:50–3:10 Benchmark 与证据矩阵（PPT P12-P14）

"30 案例 SWE-bench dev 正式计分：edit-based 补丁引擎把闭环率从 V0.8 的 0% 提升到 10%——3/30 案例真实闭环修复，全是 devorbit 方法，single-agent 同模型同预算 0/30。三维消融可查：管道维度 diff-based 0% vs edit-based、模型维度 glm/deepseek/qwen3:8b、架构维度 devorbit vs single-agent。失败知识自沉淀：42 条 negative Episode 自动生成，第二轮按仓库召回警示注入 patch 提示。MTTR 从 3250 秒降到 17.5 秒——含真实闭环案例。误发布率 0。113/113 单元测试、9/9 对抗安全、18/18 AgentTeams 运行时、GitLab CE 真实 e2e 17/17，全部可以在仓库里一键重放。"

## 录制版新增分镜（V1.0.0）

**skill-trace（59.4s 起）Skill 调用证据**：滚动到 Skill 资产区与协同轨迹——8 个 Skill 全部版本化管理，每条 trace 记录 `skillVersion + skillDigest`，任何业务结果可定位到产生它的 Skill 版本（`reports/skills-registry.json` 为注册表证据）。

**self-healing（74.0s 起）异常处理演示**：现场运行 self-healing 场景——第一版补丁 CI 红（3 项失败）→ 失败日志回传 Patch Worker → 二次生成补全幂等保护 → CI 绿（4/4 通过）→ 审批 → 灰度 → 知识沉淀。3 次尝试仍失败则熔断降级 needs_human。

## 3:10–3:25 对比与诚实边界（PPT P14-P15）

"为什么不是单 Agent？生成与验证会同源偏差。为什么不是固定工作流？低置信只能停机等待。我们同时把已验证与尚未验证分开：AgentTeams 是官方软件本地实跑，DB Branch 是本地 PostgreSQL 等价语义，GitLab 自愈 e2e 脚本就绪、凭据注入即跑。"

## 3:25–3:30 结尾（PPT P16）

"DevOrbit 不替代专家判断——它把判断所需的证据、动作的边界和结果的验证组织起来。有依据、有边界、可验证。"

## 高频问答

**这是规则引擎还是 Agent？** 默认无密钥 Demo 用确定性 Worker 运行器确保人人可复现；V0.8 同时在本地官方 AgentTeams v1.2.2 上实际运行 QwenPaw + `deepseek-v4-flash-0731`。V0.9 进一步引入动态补证与自愈闭环：RCA 置信度不足时不再直接停止，而是自主生成诊断计划反向拉取深层 Trace（Red→补证→置信度升级）；Patch↔Verify 失败时不再直接停止，而是带失败日志反馈迭代生成（Red→Red→Green），3 次尝试后熔断降级。这些是状态机回边驱动的自主决策，不是写好的直线脚本。

**动态补证怎么做的？** 证据池分两层：surface 层只有表象日志（网关 502、p95 飙升），可能误导为"下游超时"。RCA 初始置信度 0.58 < 0.80，进入 `evidence_gathering` 状态，生成补证计划（假设→缺失证据→查询参数），反向调用 `observability.fetch_signals(granularity:'deep')` 拉取配置变更记录、连接池水位 Trace 和微服务链路 Trace。合并后重评分至 0.91，根因确认为"连接池缩容 + 幂等重试放大"。最多 2 轮，仍不达标熔断 needs_human。

**RAG 是否只是固定答案？** V0.9 知识库从 4 条扁平案例升级为 6 条结构化 Incident Episode（含服务拓扑、竞争假设、正反补丁、负面方案、观察窗口）。检索先按租户→服务→环境→git/config 版本硬过滤，再走词法+embedding 混合召回，返回 `recommendations`（成功方案）与 `warnings`（负面方案警示）。不同服务版本相同报错不会误召回。Episode 写入即 `pending` 不进默认召回，观察窗口+复盘通过转 `active`，回滚/复发转 `negative` 立即可召回作警示。

**数据库怎么验证？** 针对 Schema 变更/慢 SQL/数据污染类缺陷，从脱敏基线拉出 Branch-A（索引优化）/Branch-B（分页改写）隔离分支，重放事故流量，断言报错消失、外键完好、锁等待正常，自动比对执行开销淘汰引发死锁的方案，最优 Migration 提交 L2 审批。本地 Docker PostgreSQL 实现等价语义，生产路径为 PolarDB Agentic Database Branch。

**证据能被篡改吗？** 不能。V0.9 司法级 Hash 证据链从问题摄入→信号快照→git SHA→patch→测试→HMAC 审批→灰度指标→Episode 全链路 sha256 链式校验，`npm run verify-evidence-chain` 独立复核，篡改任一环节立即可检出（9 个对抗案例含 Hash 链篡改检测）。

**AgentTeams 体现在哪里？** 锁定官方 v1.2.2 commit `849182a`：本地 Team 为 Active，Leader Ready、7/7 Worker Ready；Leader 经 TeamHarness 建立顺序 DAG，任务通过 Matrix 发给完整 Worker ID，7 个 Worker 以独有身份调用 DevOrbit MCP 并提交状态。冻结报告含 31 条 TeamHarness、7 条 Worker Matrix 事件和 16 次 MCP 调用；另有 140/140 静态契约检查。它是官方软件本地实跑，不是云账号或生产集群。

**MCP 是真的还是接口图？** `/mcp` 是同时支持 `2025-06-18` 与 `2025-11-25` 的 Streamable HTTP JSON-RPC 端点，支持初始化、绑定 Worker 身份和协议版本的会话、工具发现/调用、输入输出 Schema、结构化结果、Origin 校验和会话销毁。服务端 Agent×Tool allowlist 和签名审批不信任 Worker 自报结论。默认成功路径含 15 条审计；官方 AgentTeams 安全终态路径含 16 条。

**安全是不是 Prompt 里写一句“不要发布”？** 不是。Manager 在 RCA、测试和回滚门禁通过后签发带 Case、Action、过期时间的 HMAC 回执，Release Worker 只能消费，不能自行签发；MCP 服务端再次验签。9/9 对抗案例覆盖越权、伪造、过期、跨 Case 重放和 Schema 混淆。生产身份认证仍需由 Higress/mTLS/OIDC 提供，本地 Header 只做会话绑定。

**100% 指标可信吗？** 它只表示 7 个确定性仿真回归案例全部符合预期，并给出 95% Wilson 区间，不代表生产准确率。7 组对照/消融显示关闭核心门禁后指标降至 71.4%–85.7%；朴素单体基线为 28.6%。SWE-bench Run 7 的旧门禁通过后来被增强兼容性探针推翻；跨仓 pydicom 单次验证也在补丁契约处失败，因此没有对外报告模型成功率。公开基准已扩到 30 个公开仓缺陷并引入人工/单 Agent 对照。

**RAG 是否只是固定答案？** 知识库含 4 条团队构造案例，检索使用可复现的词法/标签评分并返回 Top-3、得分和稳定引用。Golden Cases 的 Top-1 均命中预期历史案例，但这只验证当前仿真集；公开缺陷集和 embedding 混合检索已提供对照评测。

**如何证明根因不是编的？** 每个候选都必须携带 evidence refs；低于 0.8 或证据冲突时停止自动修复，转为补证或人工。Golden Cases 评测 Top-3 命中率。

**为什么比编码 Agent 更有价值？** 编码只是中间一步。DevOrbit 覆盖信息归并、影响面、验证、发布结果确认和组织知识沉淀，并把高风险动作纳入审批与回滚。

**当前指标是真实生产数据吗？** 不是；7 个闭环指标来自团队构造仿真。SWE-bench 是真实公开缺陷：V0.9.6 在冻结的 30 案例 test split 上正式报告——edit-based 补丁引擎下 devorbit 真实闭环 3/30（10%，经 F2P+P2P 测试验证）、可应用率 56%、RCA Top-3 73.3%，single-agent 同预算 0/30；全部失败样本与三维消融公开可查，我们不声称这是官方榜单成绩。

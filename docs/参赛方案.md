# DevOrbit 参赛方案

## 1. 场景与价值

### 真实问题

一次线上缺陷的事实通常分散在用户反馈、Issue、日志/Trace、版本变更、代码仓、CI 和发布平台中。值班研发先花时间聚合和去重，再凭经验定位代码；修复后由测试、发布负责人接力确认，最后复盘材料又与执行证据脱节。现有编码助手多聚焦“生成补丁”，难以回答四个生产级问题：为什么这样改、影响哪些模块、是否真的修好、发布后是否真的恢复。

### 目标用户与输入输出

目标用户是中大型研发团队的开发、测试、发布负责人和平台工程团队。输入是多源缺陷/需求信号与工具上下文，输出不是一段建议，而是一份可执行、可验证、可审计的交付包：规范化 Case、影响图、根因证据链、补丁/回滚点、测试报告、审批和灰度结果、复盘知识卡。

### 可量化价值假设

正式评测不使用未经验证的营销数字。复赛构建 30 个公开仓库 Golden Cases，比较人工/单 Agent/多 Agent 三组：

| 指标 | 定义 | 目标 |
|---|---|---|
| 聚合准确率 | 正确归并信号对 / 全部候选信号对 | ≥ 90% |
| Top-3 根因命中率 | 正确文件/提交进入前三候选 | ≥ 80% |
| Patch 可编译率 | 补丁通过构建 / 生成补丁数 | ≥ 75% |
| 闭环成功率 | 验证并达到终态 / 全部案例 | ≥ 70% |
| 误发布率 | 门禁通过但灰度退化 / 发布案例 | ≤ 5% |
| 证据覆盖率 | 关键决策含有效引用 / 关键决策 | 100% |

### 行业复制性

缺陷、需求、代码、CI、发布是软件组织共通对象。Skill 和 Adapter 分层使系统不绑定特定代码托管或研发管理产品；替换接入层即可复用到互联网、金融、制造、政企等软件研发组织，也可把同一闭环用于需求变更影响分析。

## 2. 方案设计

### 总体架构

```text
Issue / 反馈 / 日志 / Trace / 变更
                 │
        AgentTeams Manager
       ┌─────────┴─────────┐
       │  Case State/Room  │ ← 人类观察、审批、纠偏
       └─────────┬─────────┘
  Intake → Impact → RCA → Patch → Verify → Release → Learn
       │      Agent 通过版本化 Skill 调用稳定能力      │
       └──────────────┬──────────────────────────────┘
            MCP 2025-06-18 Adapter Layer
  Issue │ Observability │ Repository │ CI │ Release │ Knowledge
                       │
   Trace / Log / Metrics / Evidence / Approval / Artifact
```

### AgentTeams 映射

- 角色编排：一个 `devorbit-lead` Team Leader 对七个单职能 Worker；Worker spec 声明身份、运行时和 MCP 连接，Worker ZIP/Skill 清单声明可分发能力、依赖和决策边界。
- 任务拆解：Manager 根据 Case 状态图下发阶段任务；影响分析与知识检索可并行，写操作保持串行。
- 上下文传递：一案例一协作房间，结构化 Case State 是唯一事实源；消息只传引用和必要字段，原始大对象保存在证据存储。
- 协同执行：Worker 完成后发回 `status / data / evidence_refs / error`；Manager 校验 Schema 后推进状态。
- 状态追踪：所有转换写入 append-only Trace。人类能观察房间、补充证据、批准/拒绝高风险动作。

### 主路径与异常分支

主路径为 `received → triaged → diagnosed → planned → verified → approval_pending → canary → confirmed → learned`。

- 输入字段缺失：隔离坏记录，其余信号继续；输出数据缺口。
- 相似案例冲突：不强行合并，由人确认。
- 根因低置信或证据冲突：停止自动修复，回到采证或人工诊断。
- 补丁越界：若修改影响图以外的敏感目录，风险升级。
- 测试失败/超时：超时重试两次；仍失败退回 Patch Agent。
- 审批拒绝/超时：保持 `approval_pending`，不调用发布工具。
- 灰度退化：自动触发预置回滚，并生成失败复盘。

## 3. Skill 与工具集成

### 核心 Skill

七个自定义核心 Skill 覆盖 SignalFusion、ImpactMap、EvidenceRCA、PatchPlan、TestGate、ReleaseGuard 和 KnowledgeCard。另将官方门户 `alibabacloud-sls-query` v0.0.2 的可审计合规裁剪快照分发给 Intake/RCA：核心 `SKILL.md` 未修改，唯一移除路径、门户原包和分发包摘要均披露；真实部署显式配置 SLS 后，以 `GetIndex` 和 `GetLogsV2` 最小只读权限获取日志证据；当前无密钥 Demo 使用 Fixture-backed Observability MCP，未伪装成云端调用。完整 I/O、调用条件、依赖、失败处理和权限边界见《Skill 清单》。自定义 Skill 采用语义化版本和 Golden Case 门禁；官方 Skill 固定版本、门户内容哈希、归档哈希及回滚快照。

### 外部工具契约

六类 Adapter 均接入一个可运行的 MCP 2025-06-18 Server，共提供 10 个 Tool：Issue/反馈与观测信号拉取，仓库读取、隔离、写入、销毁，CI 测试，历史案例检索/写回和灰度决策。当前工具底层使用本地 Fixture/Mock，服务支持 `initialize`、`tools/list`、`tools/call`、会话、协议版本、Origin 校验、幂等重放和结构化输出；HTTP 入口为 `/mcp`。

```json
{
  "tool": "release-adapter",
  "operation": "promote",
  "input": {"version": "...", "canary": "10%"},
  "trace_id": "...",
  "idempotency_key": "case+action+version",
  "dry_run": false,
  "approval_id": "APR-..."
}
```

当前本地 MCP 不需要外部密钥，仅允许本地 Origin；生产环境由网关注入短期、范围受限凭据，Worker 不持有真实密钥。每次 Tool 调用记录协议版本、工具、Agent、Trace/Case、时延、I/O 摘要、幂等键与审计引用。写仓库、运行 CI、灰度和知识写回均通过 `tools/call`，而非 Worker 裸调内部函数。

V0.5 已将 Fixture-backed handler 抽象为六类可注入 HTTP Provider，并发布 OpenAPI 3.1 契约。完整闭环经过真实本地 HTTP Server：17 个请求覆盖 Issue、Observability、Repository、CI、Knowledge、Release，包含一次只读 POST 503 和一次幂等写 503 的安全重试；所有写请求携带幂等键，所有请求传播 Bearer 与 Case/Trace/Agent 关联，内部 HMAC 审批令牌在策略层验证后不跨越外部信任边界。契约校验为 66/66，MCP 仍保留 15 条权威审计。该证据证明外部平台可替换性，不表述为已经接入真实 GitHub/Jenkins/Kubernetes。

### 上下文与 RAG

初赛已实现共享状态、轨迹持久化和知识库 RAG。知识库含 4 条团队构造历史案例，RCA Worker 通过 MCP 检索 Top-3，输出分数和稳定引用，首条历史案例成为可复核辅助证据；低置信场景即使检索命中也不会越过 0.80 现场证据门禁。Learning Worker 把成功发布或失败回滚卡写回同一索引。当前采用词法/标签检索；7 个 Golden Cases 的 Top-1 命中和引用有效率均为 100%，但不外推为生产准确率。

### 可观测设计

每次运行生成统一 `trace_id`。当前 V0.4 已将 Agent 和 MCP Tool 调用导出为 OTLP JSON 形态的 `resourceSpans`，使用 `gen_ai.operation.name`、`gen_ai.agent.name`、`gen_ai.tool.name` 等语义属性，并输出工具调用、策略拒绝、证据引用、人工审批和 Agent 调用等 Metrics；工具 Span 通过 `parentSpanId` 归属 Worker Span。文件见 `reports/otel-happy-path.json`，命令为 `npm run export-otel`。生产可直接由 Collector 转发至 AgentScope Studio、LoongSuite 或其他 OTLP 后端。Token/费用字段在未接入真实模型前不伪造，列入复赛接入项。

## 4. 安全边界与治理

| 等级 | 动作 | 自动化边界 |
|---|---|---|
| L0 | 读取 Issue、日志、代码、知识 | 自主执行 |
| L1 | 沙箱建分支、应用补丁、运行测试 | 自主执行，命令/目录白名单 |
| L2 | 可逆配置、预发或生产小流量灰度 | 强制人工审批、幂等、回滚点 |
| L3 | 生产数据写入、不可逆变更、全量发布 | 仅生成方案，禁止自动执行 |

发布门禁同时要求根因置信度、测试、审批和回滚能力；任意一项缺失都 fail closed。审计日志追加写、敏感字段脱敏，案例级权限隔离。异常时可退化为只读诊断和人工执行，不以“自动化率”牺牲安全。

## 5. Demo 与验证证据

当前 V0.4 支持 `npm start` 一键运行，无 API Key、数据库或云资源。七个独立 Worker 经 Team Leader 分派任务，共享 Case State，并以父子 Span 记录输入/输出摘要和证据。MCP 服务端执行 Agent×Tool 最小权限、Case scope、签名审批、过期回执和输入/输出 Schema 校验。Patch Worker 经 MCP 在样例仓复现 3 个失败，再修改两个文件；Verify Worker 通过 MCP CI Tool 执行同一批 `node --test`，得到 4 项全绿。发布流程在同一 Case/Trace 上暂停并等待批准或拒绝。

自动评测包含 7 个团队构造仿真 Golden Cases：正常放量、待审批、审批拒绝、根因低置信、真实测试失败、灰度回滚和坏输入隔离。目前完整策略 7/7 通过、5/5 安全分支正确、Worker 证据覆盖率和 RAG 引用有效率均为 100%。新增 7 组对照/消融：关闭证据、测试、审批或灰度门禁后安全/决策准确率降至 71.4%–85.7%，朴素单体基线为 28.6%；结果含 95% Wilson 区间，明确不外推生产收益。另有 6/6 对抗安全案例覆盖越权、伪造/过期/跨 Case 审批和 Schema 混淆。协议冒烟验证 MCP Origin、会话身份绑定、10 个工具发现、调用、策略拒绝、路径逃逸防护、错误和销毁。另有 AgentTeams v1.2.2 的 140/140 资源/包/Skill 契约检查，以及两阶段部署编排冒烟。边界声明：案例和发布指标均为仿真，契约/编排检查不代表官方集群已运行或云账号已调用；本地运行器没有伪装成已启动官方 AgentTeams 集群，外部平台行为由 Mock 提供。

工程证据还包括 4 份可回放 JSON 运行报告和独立端口 API 冒烟测试。API 测试验证审批前后 Case/Trace ID 不变、真实测试门禁阻止发布、评测报告可访问。

V0.5 还提供非 root、只读兼容 OCI 容器。14/14 容器门禁在 UID 10001、只读根文件系统、限额 `/tmp`、cap-drop ALL、no-new-privileges、PID/内存限制下完成健康检查、控制面鉴权、3→4 Red→Green、同 Case/Trace 审批续跑、发布确认、知识写回、工作区清理、15 条 MCP 审计和 31 个交互闭环 OTLP Span。当前 Docker daemon 的旧代理不可达，因此已记录的运行证据使用本机缓存 Node 22.18.0 与已有 Debian 12 镜像构造的临时离线基础；正式 Dockerfile 默认 `node:22.18.0-bookworm-slim`，其 digest/SBOM/CVE 扫描仍需联网 CI 完成。

## 6. 开放计划与里程碑

| 阶段 | 可运行成果 | 验证成果 | 开放成果 |
|---|---|---|---|
| 初赛 V0.4 | 独立 Worker、真实补丁测试、MCP/RAG、策略门禁 | 7 闭环 + 4 RAG + 7 组消融 + 6 安全案例 + OTLP | Agent/Skill、MCP Server、Schema、策略、Worker 包、报告 |
| 复赛 V0.5 | AgentTeams 部署、真实 Git/CI、RAG | 30 个 Golden Cases、对照评测 | Adapter SDK、评测脚本、部署模板 |
| 决赛 V1.0 | 真实缺陷现场演示、可观测看板 | 故障注入、失败回滚、安全测试 | 插件市场包、贡献指南、社区路线图 |

公开基准协议已先行开源：`evaluation/public-benchmark.manifest.json` 记录来源、许可证、固定提交、测试补丁、预期修复提交和 train/validation/test split；`schemas/public-benchmark.schema.json` 与 `schemas/public-benchmark-results.schema.json` 约束数据和运行结果；`npm run public-benchmark` 拒绝未知 Case、重复运行、split 泄漏、缺少 Runner commit 和 dataset 不匹配。当前由于网络不可用且未冻结公开快照，报告状态为 `not_run`，没有公开数据分数。冻结后同一协议比较 human、single-agent 和 DevOrbit，并报告 Wilson 区间、Bootstrap 区间、分母和排除原因。

以 Apache-2.0 开放自研代码和文档。当前无商业 API、闭源模型和第三方 npm 依赖；数据全部为团队构造。真实 AgentTeams、模型、数据库和可观测组件接入时逐项披露版本、许可证、费用、权限和替换成本。
